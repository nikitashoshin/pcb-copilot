# PCB Copilot — MVP Scope

## 1. Цель MVP

Цель MVP — проверить, нужен ли пользователям веб-сервис, который помогает быстро сформировать архитектуру типовой платы, список функциональных блоков, BoM и инженерные предупреждения.

MVP должен доказать базовую ценность:

> Пользователь вводит параметры типовой платы, а система за несколько секунд выдаёт структурированный инженерный черновик.

---

## 2. Первый демонстрационный сценарий

MVP поддерживает один основной сценарий:

**Промышленный контроллер на STM32**

Исходные требования:

- тип устройства: industrial controller;
- входное питание: 24 В DC;
- внутренние питания: 5 В и 3,3 В;
- микроконтроллер: STM32;
- программирование: SWD;
- интерфейс: RS-485;
- дискретные входы: 4 шт., 24 В;
- релейные выходы: 2 шт.;
- индикация: питание, статус, связь;
- размер платы: 80×60 мм;
- число слоёв: 2.

---

## 3. Основной пользовательский сценарий

1. Пользователь открывает веб-приложение.
2. Переходит на страницу создания проекта.
3. Заполняет форму параметров платы.
4. Нажимает кнопку «Сформировать архитектуру».
5. Система отправляет запрос на backend.
6. Backend подбирает функциональные блоки.
7. Backend формирует BoM.
8. Backend формирует warnings и результаты проверок.
9. Frontend показывает:
   - список функциональных блоков;
   - BoM;
   - инженерные предупреждения;
   - результаты проверок;
   - дисклеймер.
10. Пользователь может скачать BoM или отчёт.

---

## 4. Функции MVP

### 4.1. Backend

Backend должен реализовать:

- API для генерации архитектуры;
- API для генерации BoM;
- API для инженерных проверок;
- API для экспорта BoM;
- API для генерации отчёта;
- хранение справочника блоков в JSON-файле;
- Swagger/OpenAPI.

На первом этапе backend может работать без базы данных и авторизации.

---

### 4.2. Frontend

Frontend должен реализовать:

- главную страницу;
- страницу создания проекта;
- форму параметров платы;
- страницу результата;
- отображение функциональных блоков;
- отображение BoM;
- отображение warnings;
- отображение check results;
- кнопки экспорта.

---

### 4.3. Библиотека функциональных блоков

MVP должен содержать начальный набор блоков:

- input_power_24v;
- reverse_polarity_protection;
- dc_dc_24_to_5;
- ldo_5_to_3v3;
- stm32_core;
- swd_connector;
- rs485_interface;
- digital_input_24v;
- relay_output;
- led_indication;
- connectors.

---

### 4.4. Базовые проверки

MVP должен выполнять минимум следующие проверки:

1. Для питания 24 В должна быть защита от переполюсовки.
2. Для питания 24 В должна быть входная защита или предупреждение о ней.
3. Для STM32 должно быть питание 3,3 В.
4. Для STM32 должен быть SWD-разъём.
5. Для STM32 должны быть развязочные конденсаторы.
6. Для STM32 должна быть цепь Reset или предупреждение.
7. Для RS-485 должна быть рекомендация по терминальному резистору.
8. Для RS-485 должна быть рекомендация по защите линии.
9. Для дискретных входов 24 В должна быть защита или согласование уровня.
10. Для релейных выходов должна быть защита катушки реле.
11. Для релейных выходов должно быть предупреждение о токе нагрузки.
12. Для всех компонентов должен быть footprint.
13. Для всех компонентов должен быть номинал или комментарий.
14. Для платы должен быть указан размер.
15. Для промышленного применения должно быть предупреждение о необходимости проверки EMC.

---

## 5. Ограничения MVP

MVP не включает:

- регистрацию пользователей;
- личный кабинет;
- PostgreSQL;
- оплату;
- полноценную генерацию KiCad-схемы;
- автоматическую трассировку платы;
- Altium;
- интеграцию с поставщиками компонентов;
- подбор реальной складской доступности компонентов;
- DRC/ERC на уровне KiCad;
- загрузку пользовательских проектов;
- PDF-отчёты.

Эти функции можно добавить после проверки спроса.

---

## 6. Критерии готовности MVP

MVP считается готовым, если:

1. Пользователь может открыть frontend.
2. Пользователь может заполнить форму первого сценария.
3. Backend принимает ProjectSpec.
4. Backend возвращает ArchitectureResult.
5. В ArchitectureResult есть список functionalBlocks.
6. В ArchitectureResult есть BoM.
7. В ArchitectureResult есть warnings.
8. В ArchitectureResult есть checkResults.
9. Frontend отображает результат.
10. BoM можно экспортировать.
11. Отчёт можно сформировать в Markdown.
12. Проект запускается локально.
13. В README есть инструкция запуска.
14. В интерфейсе есть дисклеймер о ручной инженерной проверке.

---

## 7. Технический стек MVP

Рекомендуемый стек:

- Backend: .NET 8 Web API;
- Frontend: Next.js + TypeScript;
- Data: JSON-файлы на первом этапе;
- KiCad generator: Python, на более позднем этапе;
- Docker: после появления backend и frontend.

---

## 8. Первый milestone

Первый milestone:

> Форма → JSON → functionalBlocks → BoM → warnings → checkResults → отображение на странице результата.

KiCad-генерацию добавлять только после того, как этот сценарий стабильно работает.
